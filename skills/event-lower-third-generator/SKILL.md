# Broadcast HTML graphics

You produce **on-air graphics as HTML templates**: one file per graphic, a transparent page that the playout server (CasparCG) renders over video and that a controller (Companion, Ontime, a script) fills with data. Mistakes are visible on air, so the bar is: it looks like the client's event, every text fits, nothing appears before it is called, and the operator can change every text without touching the code.

Two kinds of request:
1. **Make a package** - "from these materials prepare lower thirds for the conference", or a list of wanted graphic types. Follow the workflow below.
2. **Review / fix / extend** an existing template (often generated by another AI). Run `scripts/check_graphics.py`, then go through the rules in this file. Typical finds: plays by itself on load, fonts that don't exist on the server, clock in the server's time zone (UTC), `update()` that crashes on an empty string.

## Workflow for a package

### 1. Read the materials and write down the look
Materials can be anything: a brand book, a key visual, a poster, slides, a website screenshot, a logo, example lower thirds (from the client or stock sites), photos of the stage. They rarely contain lower thirds - your job is to **derive** a graphics language from them, not to copy a picture. Read `references/design-from-materials.md`, then write a short style sheet before any code:
- palette (4-6 colours with roles: plate, accent, text on plate, text on accent, warning/alert) - sample them with `scripts/palette.py <image>` instead of guessing hex values from a thumbnail;
- typography (the client's font if delivered as a file, otherwise the closest available one - see fonts below), weights, letter-spacing for labels;
- shapes and motifs (angles, rounded vs sharp, stripes, glows, glass, outlines), and how they translate to a lower third;
- motion character (snappy / smooth / elegant), which becomes the easing and timing tokens.
Show this to the user in a few lines if the brief is open, then continue; don't stop for approval unless something is really unclear (e.g. two conflicting brand directions).

Images with stock watermarks (Adobe Stock, Freepik, Shutterstock) are **style references only**: never embed or trace them; build the shapes in CSS/SVG yourself.

### 2. Choose the set
If the user named the types, make those. For "a set for a conference" use the default set from `references/graphics-catalog.md` (speaker, two speakers / panel, session title, announcement, break timer, ticker + clock, logo bug, next up, Q&A / social, sponsor) and mention what else is available. For TV / news / sport the catalog has other sets. Each graphic gets a field list (the JSON contract) before you write it.

### 3. Build on the starter kit
Copy `assets/kit/` (runtime `gfx.js` + `gfx-base.css`) and `assets/starter/` into the package folder and adapt. The starter templates (speaker, timer, ticker, announcement) are **tested on CasparCG 2.5.1** (rendering, data as JSON / XML / object, Companion triggers, 720p scaling); keep their mechanics and change the look. Package layout:
```
<event>/                    -> copied as a whole into CasparCG's template folder
  theme.css                 all colours, fonts, timing as CSS variables - restyle here
  kit/gfx.js, kit/gfx-base.css
  fonts/  img/              delivered fonts, logos, speaker photos (relative paths work)
  speaker.html  timer.html  ...
  data.example.json         sample data for every template (what the operator fills in)
  README.md                 operator sheet: template names, fields, Companion / AMCP examples
```
How a template is written (fields, `data-field`, `data-fit`, `is-in` / `is-out` animation classes, `render()` hooks) is in `references/template-contract.md`. Write each template so that **all visible text comes from fields** and has sensible behaviour when a field is empty (hide the element, collapse the separator).

### 4. Check
- `python3 scripts/check_graphics.py <event>/` - static checks (autoplay, fonts, external URLs, time zone, missing assets, empty update).
- Open every file in a browser with `?preview=1`: grid background, title-safe frame and a generated panel with all fields; try the longest realistic texts (long double-barrelled names, two-line titles, 3 ticker items vs 30).
- If a CasparCG server is reachable (see the `casparcg-amcp-button-builder` skill), load it there: `CG 1-20 ADD 1 "<event>/speaker" 1 "<data>"` and look at the output; HTML that works in a desktop browser can still fail there (fonts, time zone, autoplay).

### 5. Hand over
Write `README.md` for the operator: per template the CasparCG name, fields with examples, how to show / update / hide it, and ready lines for Companion (see `references/template-contract.md`, section Companion). Give the data as Companion fields with variables, e.g. `name="$(local:name)" role="$(local:role)"`, so one button per speaker differs only in its local variables.

## Rules that matter on air (tested on CasparCG 2.5.1, Chromium 142 inside)
- **Never play by itself.** The page loads hidden; `play()` is called by CasparCG (`CG PLAY`, or play-on-load in `CG ADD`). A template that animates in on load shows placeholder text on air the moment it is loaded with play-on-load 0 (seen with an AI-generated template: "Aleksandra Nowak" appeared before any data). Preview-only autoplay behind `?preview=1` is fine.
- **No placeholder text on air.** Sample names only in preview (`sample` in the field list); on air, empty fields render empty.
- **Transparent background**, design on a 1920x1080 stage (the runtime scales it to 720p / 2160p channels). Keep text inside the title-safe area (5 % per side: 96 x 54 px at 1080p) and leave room for the broadcaster's own bug.
- **Fonts**: the server only has its own fonts (a Linux CasparCG typically DejaVu and Liberation; Windows its usual set). "Segoe UI", "Inter", "Montserrat" etc. silently fall back. Ship the font file in `fonts/` with `@font-face` (relative URLs work), or use one that is installed. Don't rely on Google Fonts URLs - the playout machine is often offline.
- **Time zone**: the server often runs in UTC (the test server did). Clocks and countdowns must pass `timeZone: 'Europe/Warsaw'` (or the event's zone) - `GFX.clock()` does.
- **Text always fits**: `data-fit` shrinks long names; single-line fields get `white-space: nowrap; overflow: hidden`; multi-line fields a max line count. Test with the longest real names.
- **Data**: `update(data)` must accept an object (`CG INVOKE "update({...})"`), a JSON string, XML `<templateData>` (CasparCG clients send f0, f1...), and an empty string (CasparCG calls `update("")` after `CG ADD` without data). Text goes in with `textContent`, never `innerHTML`.
- **Animation**: CSS animations on `is-in` / `is-out` classes, entrance ~0.5-0.8 s, exit ~0.4 s, starting just outside the frame or the element's own box (an offset far outside the frame makes the motion happen off screen and the graphic seems to pop in). `stop()` plays the exit; the operator clears the layer after it (`outMs`).
- **Performance**: CasparCG renders HTML on the CPU when there is no GPU, and every loaded template is a browser page. On the test server (4 vCPU, no GPU, the channel also being recorded to a file) a 1080p50 channel with four HTML templates on air fell behind (5 s of video for 11 s of real time); the same set on a 720p50 channel kept up. Check the real machine with the full set loaded. Keep the number of simultaneously loaded templates low (clear layers that are off air), prefer solid or gradient plates to large `backdrop-filter` / `blur()` areas, and avoid continuous animations nobody needs (one ticker is fine).
